## 1. Project Overview

### Vision
CosmoQMS es un sistema interno de **producción y calidad** para un laboratorio cosmético en Colombia. Gestiona el ciclo completo de manufactura regulada: materias primas → fórmula maestra → orden de producción con batch record electrónico firmado por etapa → control de calidad → liberación de lote → trazabilidad. Está diseñado desde cero para pasar una auditoría **INVIMA / BPM cosméticos (equivalente ISO 22716)**: cada escritura sobre un registro regulado queda en una bitácora inmutable, las firmas electrónicas exigen reautenticación en el momento de firmar, y los datos de planta se capturan incluso sin señal (PWA offline-first) sin perder ni sobrescribir un solo evento.

Lo usan 8 personas: operarios de producción, jefe de planta, control de calidad, el Director Técnico/Químico Responsable (quien libera el lote), y bodega. Arranca como herramienta interna de una sola empresa, pero la base de datos es multi-tenant desde el día uno para poder ofrecerse a otros laboratorios sin reescritura.

### Goals
- Digitalizar el batch record en papel con trazabilidad completa y firma electrónica por etapa
- Reducir el tiempo de preparación de una auditoría INVIMA de días a minutos (todo exportable)
- Permitir que los operarios trabajen desde el celular en planta, con o sin conexión
- Dejar la arquitectura lista para multi-tenant (SaaS a otros laboratorios) sin migración futura

### Success Metrics
- 100% de los lotes producidos tienen batch record electrónico completo y firmado (cero registros en papel)
- Cero pérdida de eventos capturados offline al sincronizar
- Tiempo de generación de un batch record en PDF para auditoría: bajo 1 minuto
- Cero acciones sobre tablas reguladas sin entrada correspondiente en `audit_log`

### 1.1 Relación con Mariposa ERP (contexto agregado 2026-09-25)

Antes de construir CosmoQMS existe **Mariposa ERP** (`programa_Cosmetico_Mariposa/server/` + `client/`): un monolito Express + Prisma + React/Vite, con arquitectura hexagonal por módulo, que ya cubre buena parte del terreno operativo de este blueprint — inventario con cuarentena/aprobado/rechazado, fórmulas maestras con semáforo INVIMA, órdenes de producción con máquina de estados server-side (`PLANIFICADO→EN_PESAJE→EN_MEZCLADO→EN_TESTEO→EN_ENVASADO→FINALIZADO`), asignación FEFO, cierre transaccional, y — en una rama ya lista para fusionar — los mismos 6 roles de este blueprint (`operario, jefe_planta, calidad, director_tecnico, bodega, admin`) sobre Supabase Auth.

Lo que Mariposa **no** tiene, y que es la razón de ser de este blueprint, son tres pilares estructurales completos:

1. **Trazabilidad regulatoria inmutable** — bitácora `batch_events` append-only, `audit_log` transaccional, firmas electrónicas con reautenticación (`reauth_verified` + `meaning_statement`). Mariposa hoy guarda el mezclado como un campo JSON sobrescribible y no tiene firmas ni auditoría genérica.
2. **Captura offline-first en planta** — cola local (Dexie) + service worker + sync idempotente por `clientEventId`. Mariposa es un SPA de Vite normal: sin conexión, se pierde la captura.
3. **Multi-tenant real** (`organizations` + Row Level Security por `tenant_id`). Mariposa es de una sola empresa, sin ningún concepto de tenant.

**Decisión de alcance (2026-09-25):** CosmoQMS se construye como **proyecto completamente aparte** — carpeta hermana de `programa_Cosmetico_Mariposa` (no anidada), repo git propio, proyecto Supabase propio, app Clerk propia. No se toca ni se depende en tiempo de ejecución de Mariposa ERP. Al mismo tiempo, el diseño se mantiene **modular a propósito** para poder adherirlo a Mariposa más adelante sin reescritura, mediante tres mecanismos ya incorporados en el modelo de datos y la arquitectura (Secciones 3–6): `organizations` permite que el laboratorio de Mariposa se convierta en el tenant #1 el día que se decida migrar; cada dominio de negocio es un router tRPC independiente sin imports cruzados, adoptable uno a la vez; y el vocabulario de entidades (Sección 4.1) se mantiene deliberadamente cercano al de Mariposa para que una futura migración de datos tenga un mapeo de campos obvio en vez de una traducción desde cero.

## 2. Tech Stack

| Layer | Technology | Why |
|-------|-----------|-----|
| Framework | Next.js 15 (App Router) | Un solo código sirve la web de escritorio (oficina/calidad) y la PWA instalable en celular (planta) |
| Language | TypeScript (strict) | Tipado fuerte crítico para cálculos de fórmula, tolerancias de pesaje y firmas |
| Styling | Tailwind CSS v4 | Sistema de diseño basado en tokens, consistente entre escritorio y móvil |
| Components | shadcn/ui + TanStack Table | `DataTable` para listados densos de lotes/materias primas; formularios accesibles con validación inline |
| PWA / Offline | Serwist (service worker) + Dexie.js (IndexedDB) | Cola local de eventos append-only cuando no hay señal en planta; sincroniza al reconectar sin sobrescribir nada |
| Database | PostgreSQL (Supabase) | Row Level Security aplica el aislamiento multi-tenant a nivel de base de datos, no solo de código — defensa en profundidad para datos regulados |
| ORM | Prisma | Mejor velocidad de desarrollo y migraciones versionadas; SQL crudo solo en reportes de trazabilidad complejos |
| Auth | Clerk (Organizations + MFA) | Cada empresa futura = una Organization aislada nativamente; MFA obligatorio para Calidad/Dirección Técnica; step-up de reautenticación al firmar |
| API | tRPC (mutaciones/queries internas) + REST idempotente (`/api/sync/events`) | Tipado extremo a extremo + endpoint de sincronización offline con dedupe por `client_event_id` |
| PDF | Playwright (HTML → PDF) | Batch record firmado, certificados de análisis, exportables para el auditor |
| Hosting | Vercel (app) + Supabase (BD/Storage) | Cero carga operativa para un equipo de 8 sin IT dedicado; backups automáticos, región `sa-east-1` (más cercana a Colombia) |
| Package Manager | pnpm | Instalaciones rápidas, monorepo-ready si se necesita después |

### 4.1 Mapeo de entidades con Mariposa ERP (agregado 2026-09-25)

Referencia para una futura migración de datos — ninguna fila de esta tabla es una dependencia hoy, solo documenta la equivalencia conceptual encontrada al comparar ambos modelos:

| CosmoQMS | Mariposa ERP (`server/prisma/schema.prisma`) | Diferencia relevante |
|---|---|---|
| `organizations` | *(no existe)* | Mariposa es de una sola empresa; no hay concepto de tenant |
| `users` + `role` | `Usuario` + `RolUsuario` (rama `auth-roles`) | Mismos 6 valores de rol, distinto casing (`operario` vs `OPERARIO`) |
| `raw_materials` | `Insumo` | Insumo cubre también envases/empaques, no solo materia prima |
| `raw_material_lots` | `Lote` | Estados equivalentes: `cuarentena/liberado/rechazado` ≈ `CUARENTENA/APROBADO/RECHAZADO` |
| `master_formulas` | `FormulaMaestra` | Mariposa no tiene `status: draft/active/archived` — cualquier fórmula es usable hoy |
| `formula_ingredients` | `IngredienteFormula` | Mariposa no valida que los porcentajes sumen 100% |
| `production_orders` | `OrdenProduccion` | Nombres de etapa distintos, mismo principio de máquina de estados estricta |
| `batch_events` | *(no existe — ver `bitacoraMezclado Json?` en `OrdenProduccion`)* | Mariposa sobrescribe un campo JSON; no es append-only ni cubre todas las etapas |
| `batch_signatures` | *(no existe)* | Sin concepto de firma ni reautenticación |
| `qc_results` | `phMedido`/`densidadMedida`/`resultadoCalidad` en `OrdenProduccion` | Mariposa guarda solo la última medición, no un historial |
| `deviations` | *(no existe)* | Sin flujo de desviación/CAPA |
| `finished_product_lots` | `ProductoTerminado` | Equivalente directo |
| `audit_log` | *(no existe)* | Solo `createdAt`/`updatedAt` por fila, sin bitácora transaccional genérica |
| `sops` / `sop_acknowledgments` | *(no existe)* | Módulo entero ausente |

### Relaciones clave
- `organizations` 1—N todo lo demás (multi-tenant por `tenant_id`)
- `master_formulas` 1—N `formula_ingredients` 1—1 `raw_materials`
- `production_orders` 1—N `batch_events` (histórico completo e inmutable del lote)
- `production_orders` 1—N `batch_signatures` (una firma por etapa completada)
- `production_orders` 1—N `deviations` → `deviations.approved_by` FK → `users` (rol `director_tecnico`)
- `raw_material_lots` N—N `production_orders` vía `batch_events.payload` (qué lote de MP se usó en qué pesaje)

## 5. API Design

### Rutas tRPC (internas, tipadas)
| Router | Procedimiento | Descripción | Rol mínimo |
|--------|---------------|-------------|------------|
| materials | list / getById / create / receiveLot | Materias primas e inventario | bodega |
| formulas | list / getById / create / addIngredient / activate | Fórmulas maestras | jefe_planta (activate requiere calidad) |
| production | list / create / getById / advanceStage | Órdenes de producción | jefe_planta |
| production | recordWeighing / sign | Captura de pesaje y firma de etapa | operario (+ reauth) |
| qc | listPending / recordResult / createDeviation | Control de calidad | calidad |
| deviations | approve / close | Aprobación de desviación | director_tecnico |
| traceability | byRawMaterialLot / byFinishedLot | Genealogía completa | calidad, director_tecnico |
| audit | search / export | Bitácora | admin, director_tecnico |

### REST — Sincronización offline
| Method | Path | Description | Auth |
|--------|------|--------------|------|
| POST | `/api/sync/events` | Ingesta por lote de eventos capturados offline (array de `batch_events`) | operario+ |
| GET | `/api/sync/state?since=` | Delta de datos de referencia (fórmulas activas, lotes de MP disponibles) para cachear offline | operario+ |
| GET | `/api/pdf/batch/:id` | PDF del batch record | calidad, director_tecnico |

### Detalle: `POST /api/sync/events`
```json
// Request
{
  "events": [
    {
      "clientEventId": "uuid-generado-en-el-dispositivo",
      "productionOrderId": "uuid",
      "eventType": "weighing",
      "payload": { "rawMaterialLotId": "...", "theoreticalQty": 12.5, "actualQty": 12.48 },
      "occurredAt": "2026-09-21T14:32:00-05:00",
      "deviceId": "device-uuid"
    }
  ]
}
// Response — por cada evento, aceptado o duplicado (nunca error destructivo)
{
  "success": true,
  "results": [{ "clientEventId": "...", "status": "accepted" | "duplicate", "serverId": "..." }]
}
```
**Reglas de validación:** `clientEventId` es `UNIQUE` en BD — un reintento de red nunca duplica el evento (`ON CONFLICT DO NOTHING`, se responde `duplicate`). El endpoint es la única puerta de entrada para eventos offline y corre bajo la misma máquina de estados que las mutaciones tRPC — nunca confía en el `status` que venga del cliente.

- **tRPC + TanStack Query** en las pantallas interactivas (batch record, formularios) — cache e invalidación automática tras cada mutación
- **Dexie (IndexedDB)** como fuente de verdad local cuando no hay red; el `sync-engine.ts` reconcilia contra el servidor al reconectar, siempre en modo *append*, nunca *overwrite*
- **Zustand** solo para UI efímera (estado del `OfflineIndicator`, panel activo) — nunca para datos de negocio

## 8. Authentication & Authorization

### Auth Flow
Login vía Clerk → si el rol es `calidad` o `director_tecnico`, MFA obligatorio (TOTP) → selección automática de Organization (tenant) según membresía → redirect a `/dashboard` con navegación filtrada por rol.

### Protected Routes
Todo bajo `(app)/` requiere sesión activa — `middleware.ts` verifica sesión Clerk + resuelve `tenant_id` desde la Organization activa y lo inyecta en el contexto de Prisma (`SET LOCAL app.current_tenant_id`). `/login` es la única ruta pública.

|------|--------|

## 9. Build Order

**Step 1 — Scaffolding**
Se crea como carpeta **hermana** de `programa_Cosmetico_Mariposa` (no anidada dentro), con su propio repo git — ver Sección 1.1. `pnpm create next-app cosmoqms --typescript --tailwind --app`. Instalar shadcn/ui (`npx shadcn@latest init`), configurar path alias `@/`, Prettier/ESLint estrictos. Cargar tokens de diseño (Sección 7) en `tailwind.config.ts` y `globals.css` (light + dark).

**Step 2 — Base de datos y multi-tenant**
Crear proyecto Supabase (región `sa-east-1`). Escribir `prisma/schema.prisma` completo (todas las entidades de la Sección 4). `prisma migrate dev --name init`. Activar RLS y escribir la policy de aislamiento por `tenant_id` en cada tabla (patrón de la Sección 4).

**Step 3 — Auth (Clerk)**
Instalar `@clerk/nextjs`. Configurar Organizations, roles custom (`operario`, `jefe_planta`, `calidad`, `director_tecnico`, `bodega`, `admin`), forzar MFA por rol. `middleware.ts` protege `(app)/*` y resuelve tenant. Webhook `/api/webhooks/clerk` sincroniza usuarios/organizaciones a la tabla `users`/`organizations`.

**Step 4 — Shell de la aplicación**
`Sidebar` con navegación filtrada por rol, `Header`, `ThemeProvider` (dark mode), layout responsive mobile-first. `OfflineIndicator` visible en todo momento (aunque su lógica real llega en el Step 11).

**Step 5 — Materias primas e inventario**
CRUD completo de `raw_materials` y `raw_material_lots`. La recepción es un **formulario manual por defecto** (no todas las materias primas llegan con QR/código de barras del proveedor) — captura código de lote, proveedor, cantidad, vencimiento, COA. Si el empaque del proveedor sí trae un código, un botón "Escanear" opcional lo lee y precarga el formulario, pero nunca es obligatorio. Al guardar, el sistema **siempre** genera e imprime su propio QR interno (`qr_code`) para ese lote, exista o no un código del proveedor. Flujo cuarentena → liberado con quién y cuándo.

**Step 6 — Fórmulas maestras**
CRUD versionado de `master_formulas` + `formula_ingredients`. Validación: la suma de porcentajes debe ser 100% (± tolerancia configurable) antes de permitir `status = active`. Solo fórmulas `active` aparecen al crear una orden de producción.

**Step 7 — Órdenes de producción y Batch Record**
Crear orden desde fórmula activa. Construir la pantalla `/produccion/[id]` con `StageTracker` y la máquina de estados server-side (`planificado → pesado → mezclado → envasado → calidad → liberado/rechazado`) — las transiciones se validan en el backend, nunca se confía en el estado que envía el cliente.

**Step 8 — Firmas electrónicas**
`SignaturePad`: al completar una etapa, exige step-up de reautenticación de Clerk + `meaning_statement` explícito → inserta en `batch_signatures`. Ninguna transición de etapa se persiste sin firma válida.

**Step 9 — Control de calidad**
`qc_specifications` por fórmula, `qc_results` por lote, cola de pendientes en `/calidad`. Un resultado `fail` bloquea el avance del lote hasta resolución.

**Step 10 — Desviaciones y CAPA**
Flujo completo: detección → investigación → acción correctiva/preventiva → aprobación obligatoria de `director_tecnico` → cierre. Una desviación abierta bloquea la liberación del lote asociado.

**Step 11 — PWA y offline**
Configurar Serwist (manifest + service worker instalable). Modelar `lib/offline/db.ts` con Dexie (misma forma que `batch_events`). Implementar `sync-engine.ts`: cola local → push a `/api/sync/events` al reconectar, con `clientEventId` para dedupe idempotente. `QRScanner.tsx` con `getUserMedia` + `zxing-js` para escanear materia prima/lote desde el celular **como atajo**; construir siempre junto a él `LotManualSearch.tsx` (buscar por nombre/código/proveedor con autocompletado) en la misma pantalla, ya que varios lotes de materia prima llegan sin QR del proveedor y algunos operarios pesarán antes de que la etiqueta interna esté impresa/pegada. Ninguna pantalla de captura depende exclusivamente de la cámara.

**Step 12 — Trazabilidad**
Query de genealogía bidireccional: desde un lote de materia prima → qué lotes de producto terminado lo usaron; desde un producto terminado → qué materias primas y proveedores intervinieron. Esencial para un escenario de retiro de producto.

**Step 13 — Auditoría**
Middleware de Prisma (`$use`) que, en la misma transacción de cualquier mutación sobre una tabla regulada, escribe una fila en `audit_log` (usuario, tabla, acción, valores antes/después, timestamp). Pantalla `/auditoria` con filtros y export CSV.

**Step 14 — Reportes y PDF**
`lib/pdf.ts` con Playwright: batch record completo (todas las etapas, pesajes, firmas, resultados QC) → PDF. Certificado de análisis. Dashboard con KPIs (rendimiento por lote, tasa de desviaciones, tiempo promedio de liberación).

**Step 15 — Pulido y despliegue**
Loading/empty/error states en todas las pantallas. Seed de datos de prueba. Deploy a Vercel + variables de entorno + dominio. Smoke test manual del flujo completo: recepción de MP → fórmula → orden → pesaje offline → sincronización → firma → QC → liberación → PDF.

## 16. Reglas No Negociables

1. **`batch_events` es append-only.** Nunca `UPDATE` ni `DELETE` — toda corrección es un nuevo evento compensatorio. Es la base de la integridad de datos exigida por INVIMA.
2. **Auditoría obligatoria en la misma transacción.** Cualquier escritura sobre una tabla regulada debe generar su fila en `audit_log` atómicamente — si la auditoría falla, la mutación falla.
3. **Firma electrónica = reautenticación + declaración de significado.** Sin `reauth_verified = true` y sin `meaning_statement`, no hay firma válida, y sin firma no hay transición de etapa.
4. **Row Level Security por `tenant_id` en cada tabla, sin excepción.** El `service role` de Supabase nunca se expone a una ruta invocada por un usuario final.
5. **Las transiciones de estado de un lote se validan en el servidor.** El cliente nunca decide en qué etapa está un batch.
6. **Idempotencia en la sincronización offline.** `client_event_id` único, `ON CONFLICT DO NOTHING` — cero duplicados, cero pérdida de eventos.
7. **TypeScript strict, cero `any`.**
8. **Una fórmula maestra solo se activa si sus porcentajes suman 100% ± tolerancia.**
9. **Mobile-first y accesible.** Touch targets ≥44px, contraste 4.5:1 mínimo en light y dark, iconografía SVG sin emojis.
10. **Nunca commitear `.env`.**
11. **Un componente por archivo, máximo 300 líneas.**
